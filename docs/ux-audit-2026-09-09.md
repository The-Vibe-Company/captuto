# Audit des parcours utilisateur — 9 septembre 2026

## Périmètre

Lecture des parcours et de leurs API : site public et aide, inscription/connexion,
consentement desktop, dashboard, réglages, enregistrement Mac et extension Chrome,
import des captures, éditeur Studio, génération, partage, lecture publique et export.
Corrections réalisées sur cette branche, en conservant la galerie de captures ajoutée
lors de la demande précédente. Aucun déploiement ni modification du recording de production.

Les constats ci-dessous reposent sur le code et, pour les parcours web modifiés,
sur des vérifications avec agent-browser à localhost:3680. Les données de test ont
été créées dans un guide temporaire, puis supprimées. L'appel au modèle et un échec
de sauvegarde ont été simulés dans le navigateur pour tester la reprise sans coût IA.
La route réelle de génération est également testée avec les mocks API de la suite Vitest.

## Problème principal

Le produit mélangeait trois objets sans les expliquer : les captures enregistrées,
les étapes choisies pour le guide et le texte généré. Une capture importée pouvait
aboutir à un éditeur vide, afficher « Processing » indéfiniment et pousser vers un
agent externe, alors que l'utilisateur voulait simplement choisir ses écrans.

Le parcours est maintenant : configurer le recorder → enregistrer → choisir les
captures → éditer ou générer → vérifier → partager/exporter.

## Ce qui reste à décider ou à valider

- **Documents légaux** : aucune politique de confidentialité ni CGU publiable n'est
  fournie dans le projet. Les liens cassés sont retirés ; rédiger des garanties ou
  des conditions commerciales sans informations validées ne résoudrait pas le problème.
- **Historique et dossiers** : ils ne sont plus présentés comme des fonctions
  existantes. Un vrai historique restaurable et des dossiers persistants nécessitent
  leur modèle de données, plutôt que des éléments de démonstration.
- **Validation terrain du recorder** : compilation et tests automatisés passent,
  mais cet audit n'a pas déclenché de nouvel enregistrement du bureau réel ni de
  changement des permissions macOS. La capture multi-écran, la reprise après
  coupure réseau et les permissions restent à valider dans ces conditions.
- **Paiement, emails et génération en production** : aucun paiement ni email réel
  déclenché ; le modèle externe a été simulé pour les tests d'interface. Le résultat
  n'est pas une certification de ces services externes.

## Complément : gestion du compte

Récupération par email et suppression autonome implémentées. La suppression exige
le mot de passe actuel et une confirmation, retire les données et fichiers du
propriétaire, annule ses abonnements et permet une reprise après erreur partielle.
Les uploads sont bloqués dès le début de la suppression, y compris avec un ancien JWT.
Voir [le parcours et les prérequis de déploiement](account-lifecycle.md).

Preuves : [email de récupération](../screenshots/pr-113/password-reset-sent.png),
[confirmation mobile](../screenshots/pr-113/account-delete-mobile.png),
[compte supprimé](../screenshots/pr-113/account-deleted.png).

Validation du complément : 390 tests web + 71 tests extension validés. Les parcours
email réel local → nouveau mot de passe → connexion et suppression/reprise ont été
exercés dans agent-browser sur un Supabase isolé. Aucun compte utilisateur réel n'a
été supprimé ; les trois comptes jetables ont été retirés à la fin des essais.

## Revue avant PR

- Narration alignée sur toutes les captures chronologiques avant sélection, pour
  éviter de reprendre la narration d’un écran exclu ou de décaler un ordre inversé.
- Échec de titre restauré et annulation d’une génération partiellement appliquée :
  les actions ne restent plus bloquées par un état de sauvegarde sans reprise.
- Verrouillage des écritures privilégiées pendant la suppression du compte,
  notamment pour les requêtes agent déjà autorisées.
- Migration placée après celle des révisions de guides ; validation conjointe avec
  14 assertions PostgreSQL, ajoutées aux checks CI.
